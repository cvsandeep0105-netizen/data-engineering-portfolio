Engineering Report

Enterprise AI-Powered Real-Time EV Fleet Data Platform · Final Engineering Record · September 2026

Project status: FINAL ACCEPTANCE
A production-oriented data engineering platform built around real-world electric-vehicle telemetry, streaming ingestion, distributed processing, PostgreSQL analytics, machine-learning anomaly detection, FastAPI services, React product interfaces, Docker, Kubernetes, CI/CD and security validation.

1. Executive Summary

This project demonstrates an end-to-end real-time EV fleet data platform rather than an isolated analytics or machine-learning demo. The system ingests telemetry, validates and processes data, persists operational information, generates analytical features, performs anomaly detection, exposes APIs, and presents the resulting intelligence through a web product.

The engineering objective was reliability and production-oriented design: reproducible processing, explicit data-quality gates, containerized services, Kubernetes orchestration, automated testing, dependency security validation, measurable API performance, and honest documentation of deployment boundaries.

2. Architecture

The final product chain is: Real EV Telemetry → FastAPI Ingestion → Apache Kafka → Streaming Consumer → PostgreSQL / Apache Spark / Isolation Forest → FastAPI + React Product Layer.

3. Real-World Data Foundation

The platform uses the TUMFTM electric-vehicle UDS dataset as its real-world telemetry foundation. The dataset contains measurements from seven series-production EVs: two Volkswagen ID.3 Pro Performance vehicles and five CUPRA Born vehicles.

The raw Parquet data contains approximately 98 million telemetry rows. The engineering pipeline converts the source into canonical vehicle datasets, applies explicit validation rules, and produces downstream feature and AI datasets.

4. Data Quality Engineering

Data quality is implemented as an explicit pipeline gate rather than an informal observation. The canonicalization stage processed 98,061,214 records, with 98,060,402 accepted and 812 rejected. The resulting data-quality gate passed.

5. Feature Engineering

The real-world feature layer produces 160,774 one-minute vehicle windows covering seven vehicles. Features include battery state-of-charge, battery voltage, vehicle speed, battery temperature and quality-related measurements.

The resulting feature dataset provides a stable analytical interface between raw telemetry and downstream machine-learning workloads.

6. Machine Learning / MLOps

The anomaly-detection layer uses Isolation Forest with real telemetry-derived features. The production model was trained from 8,251 quality-gated AI samples, using 6,600 training records and 1,651 evaluation records.

7. Streaming and Database Engineering

Apache Kafka provides the event-streaming layer while the consumer processes incoming telemetry into the operational data path. PostgreSQL provides persistent relational storage for application and analytical workloads.

The architecture separates ingestion, streaming, persistence and product concerns so individual components can evolve without requiring a complete system rewrite.

8. API and Product Layer

FastAPI exposes the platform's operational and intelligence interfaces. The React frontend consumes these APIs to provide fleet visibility, vehicle status, alerts, battery health and AI insights.

The final application was validated against the expected API route contract. The OpenAPI contract contains 16 expected routes with no missing routes.

9. Docker and Kubernetes

The platform is containerized and orchestrated locally through Docker Desktop Kubernetes. The deployment includes backend, frontend, Kafka, ZooKeeper, PostgreSQL, streaming/consumer services and the real-data replay path.

Persistent model storage is backed by a Kubernetes PersistentVolume/PersistentVolumeClaim using a retained host-path volume. This keeps the trained model independent of ephemeral application containers.

10. CI/CD and Security

GitHub Actions validates backend quality, frontend lint/build, dependency security, Docker builds, Kubernetes manifests and production-container packaging.

Dependency vulnerabilities were addressed incrementally. Backend dependencies were upgraded to secure versions after an audit identified vulnerable Kafka and JWT packages. Frontend dependency resolution was hardened with an explicit nanoid override. Subsequent security validation reported zero known vulnerabilities.

Container releases use immutable Git SHA tags alongside the latest tag. Security checks include dependency auditing, secret-pattern validation and package vulnerability scanning.

11. Reliability and Testing

Testing follows an incremental acceptance model: existing passing components are preserved while failing components are isolated and corrected. Contract tests, application tests, API validation, data-quality gates and deployment validation are used throughout the platform.

The final CI pipeline passed the backend, frontend, security, Docker, Kubernetes and release validation jobs after the dependency-security remediation.

13. Engineering Decisions and Trade-offs

  • Kafka: selected to model a genuine event-streaming architecture rather than direct database writes from producers.
  • Spark: used for distributed processing and scalable feature transformation.
  • PostgreSQL: provides dependable relational persistence for the operational product layer.
  • Isolation Forest: appropriate for unsupervised anomaly detection where production anomaly labels are limited.
  • Kubernetes: provides service orchestration, health management and persistent workload configuration.
  • Real-world telemetry: prevents the platform from depending entirely on synthetic demonstration data.

14. Honest Production Boundary

The platform is production-oriented and production-engineered, but its final runtime demonstration is local Docker Desktop Kubernetes. No cloud production deployment is claimed because cloud credentials and infrastructure were not provisioned for this project.

This distinction is intentional: engineering evidence is reported from verified implementation and tests rather than presenting an unexecuted cloud deployment as production.
